# Review, main, 2026-09-30

**Reviewed by**: Grok 4.6 (author on the implementing agent for uncommitted hybrid tokens)
**Scope**: 25 files, uncommitted on main
**Verdict**: Changes requested

## Summary
This slice adds JSON sign in, short HMAC access tokens, hashed refresh rotation on the same `sessions` row, and `GET /api/me`. Cookie mint stays on `transport = cookie` with a null refresh hash, and bearer load refuses non-api rows. Isolation in the handlers looks right: `/api/*` never takes a cookie jar, and `POST /api/session` is tested not to set `ecclesia_sid`. Do not merge yet. `GET /api/me` reads `Sdk.db` instead of one story, which spec 0003 forbids, and the CAS / isolation branches the spec names as critical are not covered by tests.

## Major
### 🟠 GET /api/me loads the person through `Sdk.db`, `crates/app/src/http/api.rs:175`
**Problem**: After `resolve_bearer`, the handler calls `state.sdk.db.user`. Spec 0003 key invariants say Cargo edges stay App to SDK to Domain and **API handlers call SDK stories only**. Root AGENTS.md says HTTP loads values, calls one SDK story, and paints. This proof endpoint does a second store read through the public `Sdk.db` field. `api_logout` also composes `resolve_bearer` then `logout` rather than one story.
**Why it matters**: The JSON surface is the template for later resource APIs. If Me reaches through `db`, later needs and inbox handlers will copy that and church rules will start leaking into App. Cargo still depends on `ecclesia-sdk` only, so this is not a Domain import, but it is the exact gap the spec called out.
**Suggested fix**: Add one SDK story such as `me_api(sdk, secret, access_token)` that resolves the bearer, loads the user, and returns the profile fields (or `None` for 401). Point `api_me` at that story only. Fold logout into one bearer-gated story the same way.

### 🟠 Critical auth branches have no test, `crates/app/tests/flows.rs:1430`
**Problem**: `us_api_01` covers happy sign in, Me, one sequential refresh, stale refresh 401, no `Set-Cookie` on sign in, and HTML logout-all killing the bearer. Spec 0003 critical scenarios that are missing:
- Parallel refresh with the same token (one winner, one 401)
- Two `Sdk` handles sharing one store through rotation
- Cookie session must not authorize `/api/me` (send `ecclesia_sid`, no `Authorization`)
- Access bearer must not bind as a cookie (`resolve_session` on an `api` row)
- Cookie row must not satisfy `resolve_bearer`
- Idle refresh after thirty days
- Revoke one API device from Me (`POST /session/{id}/revoke`), then bearer 401
- Password change deletes api rows
SDK only has `us_api_02` mint plus bearer decode unit tests. `TEST_SIGNAL = configured`.
**Why it matters**: Refresh CAS and cookie/api isolation are the production-harm paths. Two Fly processes agreeing on rotation is a user story in the spec. Green `us_api_01` cannot prove a concurrent loser 401s, or that a stolen HTML cookie cannot call `/api/*`.
**Suggested fix**: Add an SDK test that races `refresh_api` on one token (or two `Sdk` values on one SQLite file) and asserts one `Some` and one `None`. Add a flows case: HTML cookie against `GET /api/me` is 401; API sign in still leaves cookie routes on CSRF. Add idle and single-device revoke cases. Assert `Cache-Control: no-store` and the Me fields from AC-5, not only email.

## Minor
### 🟡 CAS success is a second read, not `rows_affected`, `crates/sdk/src/db/sessions.rs:51`
**Problem**: The rotate SQL is the right compare-and-swap (`UPDATE ... WHERE id = ? AND refresh_token_hash = ?`). `Db::execute` (`crates/sdk/src/db/query.rs:35`) returns `()` and drops `rows_affected`. Winner is inferred by selecting the row again and comparing hashes. There is also a pre-check `SELECT` before the update.
**Why it matters**: On a single primary this still fails closed for a concurrent loser (their follow-up hash will not match). A stale follow-up read can mark the real winner as a loser and leave a refresh hash in the row that no client was given, which bricks that device until password sign in. Two App processes is the case spec 0003 cares about.
**Suggested fix**: Make `execute` (or a dedicated helper) return rows affected. Treat `rows_affected == 1` as the only success. Drop the extra SELECT.

### 🟡 Unknown `/api/*` falls through to HTML, `crates/app/src/http/mod.rs:286`
**Problem**: Spec 0003 says `/api/*` returns JSON errors only. The four routes are registered on the same router as HTML, with `people::fallback` last.
**Why it matters**: A typo such as `/api/me/` or `/api/session/` becomes an HTML miss with cookie bind, which breaks the isolation story clients will assume.
**Suggested fix**: Nest `/api` with its own JSON 404 fallback, or reject unmatched `/api` paths as `{"error":"miss"}` with `no-store`.

### 🟡 Server failures use the auth miss code, `crates/app/src/http/api.rs:118`
**Problem**: Store errors on sign in, refresh, logout, and Me return HTTP 500 with body `{"error":"miss"}`. Spec lists `miss` for 401.
**Why it matters**: Native clients that branch on `error` will treat an outage as bad credentials. Status 500 is visible, but the code is wrong.
**Suggested fix**: Use a distinct code such as `error` for 5xx, keep `miss` for 401.

### 🟡 Daily touch errors are swallowed, `crates/sdk/src/identity.rs:313`
**Problem**: `resolve_bearer` and `resolve_session` ignore `touch_session` failure with `let _ =`.
**Why it matters**: Same as HTML. If touch stays broken, a live API device can still idle out after thirty days of successful reads. AC-8 wants daily touch on authenticated API reads.
**Suggested fix**: Log the error the way other SDK writes do, or fail the request if the touch write fails.

## Nits
- ⚪ `crates/app/src/http/api.rs:80`, `Authorization` scheme match is case sensitive (`Bearer ` only). RFC 6750 treats the scheme as case insensitive.
- ⚪ `crates/app/tests/flows.rs:1475`, Me JSON only asserts `email`. AC-5 also names id, name, city, region, and bio.
- ⚪ Working tree also has a large README hosting section and `app.css` / `app.js` edits that are not this token slice. Land them on their own so auth review stays small.

## Strengths
- Transport split is implemented where it counts: `resolve_bearer` requires `api` (`identity.rs:306`) and `resolve_session` requires `cookie` (`identity.rs:416`). A cookie HMAC cannot decode as `v3.at`, and an api row will not bind `ecclesia_sid`.
- Access MAC input is `at.{session_id}.{exp_unix}` with no `v3.` prefix. Dotted session ids are rejected. Refresh is `rt.` plus 32 random bytes, stored only as SHA-256 hex. Cookie INSERT now writes `transport` and a null refresh hash, so existing HTML mint stays compatible.
- `us_api_01` proves no `Set-Cookie` on JSON sign in, sequential refresh rotation, stale refresh 401, and logout-all killing the bearer on the same database as cookie register.

## Test coverage
Configured (`cargo test`). New logic that is covered: access encode/decode and dotted id reject; API mint writes `transport = api`; flows happy path plus stale refresh plus logout-all. New logic that is not covered: concurrent CAS, two SDK handles, cookie vs bearer isolation in either direction, idle, single-device revoke, password change vs api rows, `no-store`, full Me shape. Those gaps are the second Major above, not a separate verdict note.
